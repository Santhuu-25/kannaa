⚖️ Vulnerable Code vs Remediated Secure Code

Side-by-side educational comparison of vulnerable security patterns alongside their secure remediated implementations.

1. SQL Injection (CWE-89) HIGH SEVERITY
Rule: RULE-SQLI-01

Why the secure version is safer: Parameterized queries separate the SQL command structure from user data. Database drivers send parameters out-of-band so malicious inputs (such as ' OR '1'='1) are treated strictly as string literals, rendering SQL injection impossible.

❌ Vulnerable Implementation:
# Unsafe string concatenation / f-strings
query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
cursor.execute(query)
✓ Secure Remediated Implementation:
# Safe Parameterized Query
query = "SELECT * FROM users WHERE username = ? AND password = ?"
cursor.execute(query, (username, hashed_pass))
2. Hard-coded Secrets & API Keys (CWE-798) HIGH SEVERITY
Rule: RULE-SECRET-01

Why the secure version is safer: Retrieving secrets dynamically from environment variables or a secret vault prevents credentials from being accidentally committed to public or private version control repositories.

❌ Vulnerable Implementation:
# Plaintext secret committed in code
app.secret_key = "super_secret_hardcoded_key_12345"
STRIPE_API_KEY = "your_stripe_secret_key_here"
✓ Secure Remediated Implementation:
import os, secrets
app.secret_key = os.environ.get("SECRET_KEY", secrets.token_hex(32))
STRIPE_API_KEY = os.getenv("STRIPE_API_KEY")
3. Unsafe Dynamic Code Execution eval() (CWE-95) CRITICAL SEVERITY
Rule: RULE-EVAL-01

Why the secure version is safer: ast.literal_eval() safely parses strings containing Python literals (strings, numbers, tuples, lists, dicts, booleans) without executing arbitrary code, preventing Remote Code Execution (RCE).

❌ Vulnerable Implementation:
# Unsafe dynamic code evaluation
user_input = request.form.get("config")
data = eval(user_input) # RCE Vulnerability!
✓ Secure Remediated Implementation:
import ast
user_input = request.form.get("config")
data = ast.literal_eval(user_input)
4. Command Injection via shell=True (CWE-78) HIGH SEVERITY
Rule: RULE-SHELL-01

Why the secure version is safer: Setting shell=False and passing commands as argument lists bypasses system shell metacharacter expansion (`;`, `|`, `&&`), preventing command injection attacks.

❌ Vulnerable Implementation:
# Unsafe shell execution
cmd = "ping -c 1 " + user_target
subprocess.run(cmd, shell=True)
✓ Secure Remediated Implementation:
# Safe list-based subprocess
subprocess.run(["ping", "-c", "1", user_target], shell=False, check=True)
5. Weak Password Hashing MD5/SHA1 (CWE-327) HIGH SEVERITY
Rule: RULE-HASH-01

Why the secure version is safer: PBKDF2/SHA-256 and scrypt utilize salted, key-stretching iterations to defeat precomputed rainbow tables and high-speed GPU cracking tools.

❌ Vulnerable Implementation:
import hashlib
# MD5 is fast and unsalted
password_hash = hashlib.md5(password.encode()).hexdigest()
✓ Secure Remediated Implementation:
from werkzeug.security import generate_password_hash
# PBKDF2:SHA256 with auto-generated salt
password_hash = generate_password_hash(password, method='pbkdf2:sha256')
